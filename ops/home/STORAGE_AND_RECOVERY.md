# Isolated storage and recovery preparation

This template is **not installed or tested on the Shuttle**. It does not create a bucket, expose a remote route, or deploy Ente. It is a home object-store starting point after hardware and VPS inspection. The 500 GB source library remains untouched.

## Deployment gate

1. Inspect the Shuttle only after the user supplies its SSH alias. Measure free SSD space, mount type, owner, Docker/Compose versions, disk unlock, local network and actual idle/running power. Confirm a separately located full backup destination first.
2. Pin and review the official object-store image by digest. Copy `compose.storage.yaml` to `/etc/nexo-gallery/compose.storage.yaml`, create `/srv/nexo-gallery/objects` with deliberate ownership, and create a root-owned mode-0600 `/etc/nexo-gallery/storage.env` from the example. Secrets never enter Git or shell history. The image and credentials are intentionally absent here.
3. Run `docker compose -f /etc/nexo-gallery/compose.storage.yaml config --quiet` with the root-owned environment loaded. Inspect the resolved configuration **without printing credentials**. The Compose project name, network and bind path are isolated; only loopback port 3200 is bound. Verify that loopback port is free before enabling. Do not expose the MinIO console.
4. Install `nexo-gallery-storage.service` under `/etc/systemd/system/` only after the volume and image are validated. Enable it for boot, start, then check `systemctl status`, container health and `http://127.0.0.1:3200/minio/health/live` on the home host. `restart: unless-stopped` and the unit are both startup aids; test orderly stop/reboot behavior on hardware before relying on either.
5. Provision a dedicated bucket and least-privilege credentials for Museum. Museum and clients must reach the same stable TLS S3 endpoint because Museum returns presigned URLs. An outbound home tunnel and VPS ingress are **not implemented**; authenticate and rate-limit them, avoid exposing the storage console, and test the overnight offline state. A localhost endpoint cannot be used by phone clients. Museum/Postgres on the VPS require a separate isolated config after capacity inspection. None of the above is a complete deployment.

## Backup and restore runbook, untested

- Freeze new writes and wait for in-flight uploads to settle. Capture a consistent, versioned Postgres dump from the VPS, plus an object-store snapshot/copy from home and the matching server/configuration version manifest. Ente's database contains encrypted per-file keys, so objects alone do not restore a readable library. Record object counts and hashes where practical. Never put plaintext recovery keys in the object backup.
- Transfer the encrypted objects, database dump and configuration to an **offsite physical failure domain** with enough room for 500 GB plus growth and retained versions. Keep recovery material separately protected. At 10 Mb/s sustained upstream, 500 GB takes roughly 4.6 days before overhead; measure actual throughput and budget hardware/transport.
- Restore into an isolated test environment with separate names, ports and credentials. Restore the corresponding object version and database snapshot, start the same pinned Museum version, then use a newly authorized trusted client and separately held recovery material to decrypt a representative sample. Verify album membership/corrections, thumbnails, metadata and search-index behavior. Do not point the test environment at production objects or overwrite original phone libraries.
- Before updates, take a restorable snapshot and record image digests and configuration. Update one version in a test environment, validate upload/download/recovery, then roll out with a maintenance window. Rolling back a binary after a database migration may be unsafe; restore the matching database and object snapshot into an isolated environment first. Do not use `docker compose down -v`, volume prune, or in-place destructive rollback.
- Run a full clean restore before considering source deletion. Schedule periodic restore drills and alert on missing offsite backup versions. No backup has been performed yet.
