# Isolated storage and recovery preparation

This template is **not installed or tested on the Shuttle**. It does not create a bucket, expose a remote route, or deploy Ente. It is a home object-store starting point after hardware and VPS inspection. The 500 GB source library remains untouched.

## Deployment gate

1. Inspect the Shuttle only after the user supplies its SSH alias. Measure free SSD space, mount type, unlocked filesystem UUID, owner, Docker Engine/Compose versions, disk unlock, local network and actual idle/running power. Confirm a separately located full backup destination first. Require Engine 28+; older versions can expose localhost-published ports to same-LAN hosts. Independently verify LAN reachability and firewall behavior before enabling.
2. Pin and review the official object-store image by digest. Copy `compose.storage.yaml` to `/etc/nexo-gallery/compose.storage.yaml`, mount the unlocked filesystem **at** `/srv/nexo-gallery/objects` with deliberate ownership, and create a root-owned mode-0600 `/etc/nexo-gallery/storage.env` from the example. Record that filesystem's UUID as `NEXO_OBJECT_FS_UUID`; a directory on the root disk is insufficient. Install `verify_storage.py` and `check_storage_ready.py` under `/usr/local/libexec/nexo-gallery/`. If the mount path changes, change both the Compose data path and the unit's `RequiresMountsFor`. Secrets never enter Git or shell history. The image and credentials are intentionally absent here.
3. Pull the pinned image deliberately, then run `docker compose -f /etc/nexo-gallery/compose.storage.yaml config --quiet` with the root-owned environment loaded. Inspect the resolved configuration **without printing credentials**. The Compose project name, network and bind path are isolated; only loopback port 3200 is bound. Verify that loopback port is free before enabling. Do not expose the MinIO console. The startup verifier rejects a missing/wrong filesystem UUID and Engine <28. Docker itself has no restart policy for this container, so it cannot start ahead of systemd's mount check after an unclean boot.
4. Install `nexo-gallery-storage.service` under `/etc/systemd/system/` only after the volume and image are validated. Enable it for boot, start, then check `systemctl status` and the measured `http://127.0.0.1:3200/minio/health/ready` result on the home host. After verifying the host mount, the unit forces container recreation so Compose cannot reuse an older bind mount to the hidden root directory. This interrupts an existing container, so service restarts require a transfer drain. The unit fails after bounded readiness attempts (up to roughly one minute) and stops its isolated Compose project on failed startup. If any container previously wrote with the data mount absent, inspect and recover those hidden root-disk objects separately; recreation does not migrate them. Test orderly stop, daemon restart, mount failure and reboot behavior on hardware before relying on it. A later monitor must keep probing after the initial success.
5. Provision a dedicated bucket and least-privilege credentials for Museum. Museum and clients must reach the same stable TLS S3 endpoint because Museum returns presigned URLs. An outbound home tunnel and VPS ingress are **not implemented**; authenticate and rate-limit them, avoid exposing the storage console, and test the overnight offline state. A localhost endpoint cannot be used by phone clients. Museum/Postgres on the VPS require a separate isolated config after capacity inspection. None of the above is a complete deployment.

## Backup and restore runbook, untested

- Fence **all** catalog and object mutations, including uploads, album edits, deletions and background garbage collection, and wait for in-flight work to settle. While fenced, create a retained point-in-time object snapshot and a consistent Postgres dump from the VPS; record the common boundary, object version and matching server/configuration version manifest. Only then resume mutations and copy from the immutable snapshot. If the actual storage cannot retain a snapshot/version while copying, do not claim a consistent full backup; holding the barrier for a multi-day copy is not a viable routine plan. Ente's database contains encrypted per-file keys, so objects alone do not restore a readable library. Record object counts and hashes where practical. Never put plaintext recovery keys in the object backup.
- Transfer the retained encrypted object snapshot, database dump and configuration to an **offsite physical failure domain** with enough room for 500 GB plus growth and retained versions. Keep recovery material separately protected. At 10 Mb/s sustained upstream, 500 GB takes roughly 4.6 days before overhead; measure actual throughput and budget hardware/transport.
- Restore into an isolated test environment with separate names, ports and credentials. Restore the corresponding object version and database snapshot, start the same pinned Museum version, then use a newly authorized trusted client and separately held recovery material to decrypt a representative sample. Verify album membership/corrections, thumbnails, metadata and search-index behavior. Do not point the test environment at production objects or overwrite original phone libraries.
- Before updates, take a restorable snapshot and record image digests and configuration. Update one version in a test environment, validate upload/download/recovery, then roll out with a maintenance window. Rolling back a binary after a database migration may be unsafe; restore the matching database and object snapshot into an isolated environment first. Do not use `docker compose down -v`, volume prune, or in-place destructive rollback.
- Run a full clean restore before considering source deletion. Schedule periodic restore drills and alert on missing offsite backup versions. No backup has been performed yet.
